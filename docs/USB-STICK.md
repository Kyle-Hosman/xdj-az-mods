# The AZ-MODS USB stick

| Part | Source |
|---|---|
| Boot loader | `deck/payload/usr/sbin/az-usbload`, `deck/payload/usr/sbin/az-usbpick`, the units in `deck/payload/etc/systemd/system/` |
| Boot hooks | `deck/stick/deck/boot.d/*.sh` |
| On-deck helpers | `deck/stick/deck/lib/` (`az-modupdate`, `az-community`, `az-savelogs`, `az-conf.sh`, `gadget-renotify.sh`, `az-logcap.sh`, `az-sshprio`), `deck/azrs/azrs.sh` |
| USB layout of `MODS/deck/` | `deck/stage_stick.py` |
| Trust pins | `deck/make_pins.py` |
| Mods | `src/azmod/` (settings: `azmod.c`, `azconf.c`, `azfeatures.c`, `features.def`), `src/azstem/` |

[deck/README.md](../deck/README.md) is the short tour of the deck-side scripts.

## Top-level layout

```
<stick>/
  PIONEER/            rekordbox's export (the library the deck browses)
  Contents/           the tracks, wherever rekordbox put them
  MODS/               the mods, the deck-side scripts and the switches
  STEMS/              per-track stems (STEMS-FORMAT.md)
  DRUM ROLLS/         Drum Roll sample banks (DRUM-ROLLS-FORMAT.md)
```

| Folder | Read by | Notes |
|---|---|---|
| `PIONEER/`, `Contents/` | the deck software | written by rekordbox. Playlist Editing's cross-stick copy adds two things under `PIONEER/` ([below](#files-the-mods-write-elsewhere-on-the-usb)) |
| `MODS/` | the boot loader, the boot hooks, azmod | a USB counts only when its `MODS/` holds a core or a switch ([Pick one USB](#step-by-step)); an empty `MODS/` does not |
| `STEMS/` | azstem | any mounted USB; [STEMS-FORMAT.md](STEMS-FORMAT.md) |
| `DRUM ROLLS/` | azstem | any mounted USB; [DRUM-ROLLS-FORMAT.md](DRUM-ROLLS-FORMAT.md) |

- The AZ-MODS app creates `MODS`, `STEMS` and `DRUM ROLLS` at the root in those spellings.
  `STEMS/` and `DRUM ROLLS/` are found ignoring case; the loader tests `MODS` with a plain
  directory check through the USB's mount.
- The three folders are independent: stems and drum rolls are found on any mounted USB,
  so a second USB can carry them while the first carries the mods.
- rekordbox and other players ignore `MODS/`, `STEMS/` and `DRUM ROLLS/`, and an
  XDJ-AZ without the AZ-MODS firmware loader reads none of them.

## `MODS/`

```
MODS/
  azmod.so                    the core mod (required)
  azstem.so                   the audio mod (stems, Drum Roll)
  azmod-pngpatch/             art replacements the core applies at start
  deck/                       the deck-side scripts: loader, helpers, boot hooks
  community-mods/             installed community mods, each with its own data/
  azmods.cfg                  every setting and switch (below)
  uninstall                   request: take the deck back to stock
  logo.restore                request: put the stock boot logo back
  ssh.enable, authorized_keys switch + key for key-only SSH
  azstems.pair, azstems-queue/  Remote Stems pairing and request queue
  .deck-info                  written by the deck: firmware and set version
  .pending-powercycle         written by the deck: the last apply failed
  .mods-disabled-crashloop    written by the deck: this set crash-looped
  .uninstall-result           written by the deck: result of an uninstall
  az-sshgate-boot.log         written by the deck: SSH hook log
  logs/                       written by the deck: System Info > Save Logs to USB
```

### The mod set

| Path | Written by | Purpose |
|---|---|---|
| `azmod.so` | app | the core: the Mod Menu and every mod except the audio path. The loader also accepts `azmod-core.so` and prefers it when both are present. Without a core nothing loads. |
| `azstem.so` | app | stems playback, key shift for stems, the Drum Roll sampler. Optional: without it the core loads alone. |
| other `*.so` | anyone | staged into the deck's cache like the two above when the trust pins name them, never preloaded. Community mods load from `community-mods/`, never from here. |
| `azmod-pngpatch/` | app | replacements for the deck's built-in art: `N.bin` (a PNG) with `N.addr` (its address in firmware 1.30) and `N.addr.<build>` (for example `N.addr.2.00`) for other builds. Generated by the release build. The core applies the set in its constructor, before the deck's UI starts, and skips the whole set when any blob lacks an address for the running build ([FIRMWARE-SUPPORT.md](FIRMWARE-SUPPORT.md#features-that-exist-on-only-some-builds)). |

- `.so` names may contain only `A-Z a-z 0-9 . _ + -`; the loader skips anything else.
- Names starting with `.` are ignored (macOS writes `._azmod.so` beside every file on FAT
  and exFAT).

### `deck/`: the deck-side scripts

The AZ-MODS firmware carries a bootstrap copy of the loader. Everything else that runs on
the deck outside the deck software rides on the USB in `MODS/deck/`, so a fix ships with
a mods release instead of a reflash. `deck/stage_stick.py` lays the folder out; a release
adds the changelogs and the signed pins (`deck/make_pins.py`). The app installs the folder
with every mod set and deletes any file under `deck/` the set does not name.

```
deck/
  version                     the set version, e.g. 1.2.2 (one line)
  az-usbload                  the loader; the firmware copy hands over to it
  CHANGELOG.txt               release notes shown on Mod Menu > Updates
  CHANGELOG.json              the same notes for the desktop app (the deck does not read it)
  lib/az-usbpick              which stick to use (by port)
  lib/usb-renotify.sh         re-announce the sticks after an EP147 restart
  lib/gadget-renotify.sh      re-announce the computer link (SOFTWARE CONTROL)
  lib/az-modupdate            Mod Menu > Updates: download and install a newer set
  lib/az-community            Mod Menu > Community Mods: browse, install, remove
  lib/az-savelogs             Mod Menu > System Info > Save Logs to USB: copy the logs to MODS/logs/
  lib/az-logcap.sh            the size cap the deck scripts apply to their logs
  lib/azrs.sh                 Remote Stems helper (MENU > MAKE STEMS)
  lib/az-handoff-guard        the way back to the deck while a mod has the screen (the SDK's handoff)
  lib/dropbear, dropbear.LICENSE   SSH server for firmware that has none
  lib/az-sshprio              keeps SSH reachable while the deck software starts
  boot.d/05-keep-testmode.sh  keeps /tmp/testmode, which EP147.service needs to start EP147
  boot.d/10-sshgate.sh        SSH on or off, from ssh.enable + authorized_keys + the keys allowed on the deck
  boot.d/20-bootlogo.sh       restores the stock boot logo on request
  boot.d/30-uninstall.sh      removes every AZ-MODS file from the deck on request
  trust.pins, trust.pins.minisig  the SHA-256 of every file above and of the set's .so
                              files, signed with the release key
```

How the loader treats `deck/`:

| Rule | Detail |
|---|---|
| Only pinned bytes run | every file in `deck/`, and every `.so` the loader would stage, must be named with its exact SHA-256 in a genuinely signed `trust.pins`. A file that is not pinned is deleted from the RAM copy before anything runs and never reaches the cache. Without genuine pins nothing in `deck/` runs, no `.so` is staged, and the deck boots stock. The pin format, the signing and the developer override are in [UPDATES-AND-SIGNING.md](UPDATES-AND-SIGNING.md), "The deck's trust pins". |
| Copied to RAM first | the folder is copied to `/tmp/az-deck` with `._*` files removed before anything in it runs. Nothing executes from the USB. |
| Cached for USB-less boots | what passes the check is mirrored to `/home/root/settings/az-usbload/deck`, so a boot without the USB runs the last set's hooks; that copy is checked against its own pins again before it runs. A mods USB without `deck/`, or without genuine pins, removes the cached copy. An uninstall boot leaves the cache alone (the hook deletes it). |
| Chain-load | `deck/az-usbload` takes over the boot only when it is pinned and passes `sh -n`, and `azmods.cfg` sets neither `mods = off` nor `deck = off`. If it exits non-zero the firmware copy carries on. A firmware loader that predates the trust check hands over after `sh -n` alone; the USB's loader then checks its own folder before using it. |
| Hooks | `deck/boot.d/*.sh`, run with `sh` (FAT has no execute bit), one at a time in name order, stdin closed, output to `/tmp/az-usbload.log.hooks`, with a 150 second watchdog each (`AZ_HOOK_MAX`). A hook that does not parse is skipped, one that times out is killed, and neither stops the next. |

Environment the hooks get:

| Variable | Value |
|---|---|
| `AZ_MNT` | the picked USB's mount; empty when there is none |
| `AZ_PORT` | `1` or `2` |
| `AZ_MODS` | `$AZ_MNT/MODS` |
| `AZ_MODS_OFF` | `1` when `azmods.cfg` says `mods = off` |
| `AZ_STAGE` | the cache, `/home/root/settings/az-usbload` |
| `AZ_DECK` | the RAM copy, `/tmp/az-deck` |
| `AZ_LOG` | the loader's log, `/tmp/az-usbload.log` |

### Community mods

| Path | Written by | Purpose |
|---|---|---|
| `community-mods/repos.txt` | app, deck | repositories the user added, one per line |
| `community-mods/<id>/` | app, deck | one installed mod: `azmod.json`, `<id>.so`, `icon.png`, optional `shots/` and `assets/`, and `.origin` (the repository and version it was installed from; absent for a copy put there by hand) |
| `community-mods/<id>/data/` | core | created on demand for a mod's own files (its `data_dir`); never copied to the deck, never in a package, kept by an update and deleted with the mod. `.data.owner` beside it names the repository it belongs to; a `.data@<hash>/` folder holds another repository's mod's files, set aside |

A USB from a 1.2.3 test build (`MODS/community/` and `MODS/community-data/`) is moved into this
layout at the next boot, and the old folders are removed.

- Which mods load is set in [`azmods.cfg`](#azmodscfg-settings-and-switches):
  `community-mods.<id> = on` loads a mod, `community-mods.<id> = off` lists it as turned off, a mod
  with neither is not listed, and `community-mods = off` loads none (the official mods are
  unaffected). The app and the Mod Menu's Community screen write these keys.
- The loader mirrors `community-mods/` (without each mod's `data/`) into the deck's cache, and the core loads mods only from
  that copy.
- Not mirrored: `._*` files, top-level entries starting with `.` (the installer's
  `.<id>.new` and `.<id>.old`), and every mod's `assets/` folder, which the mod reads from the
  USB through `assets_dir`.
- The mirror is skipped, and the previous cache copy kept, when it would leave less than
  12 MB free on the settings partition (`AZ_COMMUNITY_P7_RESERVE_KB`).
- An enabled mod loads only when the deck's approved list
  (`/home/root/settings/azmod-community/approved`) holds its id with the SHA-256 of exactly
  its `<id>.so`. Installing or updating from the Mod Menu records the approval; a mod put on
  the USB any other way shows "New mod found: allow?" until the DJ allows it.
- The deck-side machinery is in [COMMUNITY-MODS-INTERNALS.md](COMMUNITY-MODS-INTERNALS.md);
  the package format, the repository file and the API are in the SDK (`az-mods-sdk`).

### `azmods.cfg`: settings and switches

`MODS/azmods.cfg` holds every AZ-MODS setting: the Mod Menu's rows, pad colors, pins,
community mods' Mod Menu rows (`<id>:<key>`) and the values they store (`<id>:cfg.<key>`,
`<id>:str.<key>`, `<id>:owner.repo`), which community mods load, and the switches. It
belongs to the USB, so a USB keeps its settings from deck to deck, and two USBs can
carry two different setups.

```
# azmods.cfg: AZ-MODS settings
version = 1
mods = on
stems = on
drum-roll-bank = 2
padcolor.0 = 3
pinned = stems,drum-roll-bank
community-mods = on
community-mods.glow-mod = on
glow-mod:speed = 1
glow-mod:cfg.level = 3
glow-mod:str.label = "Main"
glow-mod:owner.repo = https://raw.githubusercontent.com/someone/glow/HEAD/azmods-repo.json
```

| Rule | Detail |
|---|---|
| Lines | `key = value`. Whitespace around `=` and at both ends is ignored. `#` starts a comment line (a `#` after a value is part of the value). Keys use `a-z 0-9 . _ : -`. |
| Version | a file needs `version = 1`. Without it, or over 64 KB, or with a higher version, it is not a settings file: the deck neither imports it nor writes over it, and keeps using its own copy. |
| Duplicates | the last line of a key wins; a rewrite keeps one line per key, in its place |
| Unknown keys | kept as they are (a key of a mod that is not installed stays for when it comes back) |
| Line ends | LF; CR is ignored |

Switches:

| Key | Effect |
|---|---|
| `mods = off` | the deck runs stock: nothing is preloaded, and `deck/az-usbload` does not take over. The cache on the deck is kept, so `mods = on` (or deleting the line) brings the same set back without copying. |
| `deck = off` | do not chain to `deck/az-usbload` and do not run `deck/boot.d`; the mods still load. Read on the USB only: a boot with no USB still runs the cached hooks. |
| `community-mods = off` | no community mod loads; the official mods are unaffected |
| `community-mods.<id> = on`, `off` | one community mod on or off ([Community mods](#community-mods)) |

The switches are read by the loader before anything is staged, and from any file: a file
that holds nothing but `mods = off` (no version line) still turns the mods off. Values
`off`, `0` and `false` mean off, in any case.

Where the settings live:

| Copy | Role |
|---|---|
| `MODS/azmods.cfg` on the picked USB | the source of truth |
| `/home/root/settings/azmod.conf` on the deck | the deck's working copy: what azmod reads at start and writes on every Mod Menu change. Used as it is when no mods USB is in. |

| When | What happens |
|---|---|
| boot, and after a Community screen change | the loader compares the USB's file with the last sync. Changed (edited on a computer, written by another deck, or another USB): azmod takes it over its working copy, within a second, and applies it as Mod Menu changes would. Unchanged: nothing. |
| a Mod Menu change | azmod writes its working copy only. The loader's watcher writes it to the USB 5 seconds after the last change, once every deck is empty: as `.azmods.cfg.new`, compared, renamed over `azmods.cfg`, synced. The stock read-only mount is remounted read-write for the write and back after. A failed write is retried; a pulled USB keeps its previous file. A change made with a track loaded is written once the decks are empty, and survives a power-off in the working copy until then. |
| no `azmods.cfg` on the USB | the loader creates it from the deck's working copy |
| a file that is not a settings file | refused: not imported, not overwritten (logged in `/tmp/az-usbload.log`) |

The theme and the Fine Vinyl Speed Adjust value are in `azmods.cfg`, so they follow the USB.
Some per-deck files stay on the deck and are not in it: the Bluetooth channel
([Settings kept on the deck](#settings-kept-on-the-deck)) and the `azmod-*.off` /
`azmod-*.on` flag files, including the Themes kill switch `azmod-themes.off`.

### Requests

Tested for existence only; contents are ignored (an empty file is the convention), except
that `ssh.enable` may carry the key.

| File | Read by | Effect |
|---|---|---|
| `uninstall` | loader, `20-bootlogo.sh`, `30-uninstall.sh` | take the deck back to stock and remove every AZ-MODS file from it ([Uninstall](#uninstall)) |
| `logo.restore` | `20-bootlogo.sh` | put back the stock boot logo from the backup an early AZ-MODS firmware made. Honored even with `mods = off`. Only the two logo images and their table checksums are written, in place; the rest of the boot partition (the device tree included) is never written. The bytes replaced are saved first with a journal, and a restore cut short by a power loss is finished at the next boot. The hook deletes the file once the logo is verified back. |
| `logo.on` | nothing | obsolete, ignored |
| `ssh.enable` | `10-sshgate.sh` | turn on key-only root SSH with the key in `authorized_keys`, once that key is allowed on the deck ([SSH](#ssh)). Absent: SSH is turned off. |
| `authorized_keys` | `10-sshgate.sh` | OpenSSH public key lines (`ssh-...`, `ecdsa-...` or `sk-...`). If missing, a key inside `ssh.enable` itself is used. |
| `diag.on` | nothing in a release | `az-bootlog` reads it; the release firmware does not include `az-bootlog`, so on a release deck this file does nothing and `MODS/az-boot.log` is never written. |

### SSH

SSH is off unless the picked USB carries `MODS/ssh.enable` and a public key that has been
allowed on this deck ([Allowing a key](#allowing-a-key)). Any failure leaves it off.

| Step | What `10-sshgate.sh` does |
|---|---|
| Key | reads the key lines (`ssh-...`, `ecdsa-...`, `sk-...`) from the USB; a key already allowed on the deck goes into `/run/az-ssh/active` and is installed as root's `authorized_keys` in `/home/root/.ssh` and `/root/.ssh` (both RAM); any other key is held in `/run/az-ssh/pending` and never installed |
| Server | `/usr/sbin/dropbear` where the firmware has it (1.30); otherwise the USB's `deck/lib/dropbear` (2.00 ships none), copied to `/run/az-dropbear`. Neither: SSH stays off. |
| Host key | `/etc/dropbear` is linked to `/home/root/settings/az-dropbear`; dropbear (`-R`) creates each key type the first time a client asks for it and keeps it there, so it survives reboots and updates. The key baked into firmware 1.30's image is the same on every unit and is never used. A deck that served that image key shows ssh's "REMOTE HOST IDENTIFICATION HAS CHANGED" warning once; remove the old entry with `ssh-keygen -R <deck address>`. |
| Start | dropbear runs key-only (`-s -g`: no passwords, root password login refused) as the transient unit `az-dropbear.service`, at normal priority, and only while at least one allowed key is installed |
| Approval path | copies itself to `/run/az-sshgate` and installs `az-sshapprove.path`, which runs `/run/az-sshgate approve` when `/run/az-ssh/approve` appears |
| EP147 start window | EP147's real-time threads run with real-time throttling off and, while EP147 starts, can leave no CPU time to a normal-priority dropbear. `az-sshwindow.service` (started by an `EP147.service` drop-in before every EP147 start, and once at boot) raises only the listener to real-time priority 50 for 120 seconds, and once a second puts every other dropbear task, including everything run from a session, back to normal priority; at the end of the window the listener too (`deck/lib/az-sshprio`). Without `az-sshprio` there is no window and SSH answers once EP147 has started. |
| Off | no USB, no `ssh.enable` or no key: stops `az-dropbear.service`, removes the window, the approval path, `/run/az-ssh` and the installed keys. The allowed list is kept. |
| Log | `/tmp/az-sshgate.log`, copied to `MODS/az-sshgate-boot.log` on the USB so SSH can be debugged without SSH |

#### Allowing a key

A key from the USB logs in only after it is allowed at the deck.

| Stage | What happens |
|---|---|
| Pending | each USB key not in the allowed list is one line of `/run/az-ssh/pending`: `<fingerprint> <type> <base64>`. The fingerprint is `SHA256:` plus the base64 SHA-256 of the decoded key, as `ssh-keygen -l` prints it (without `openssl` on the deck, `KEY:` plus the last 24 characters of the key text). The hook log lists the pending fingerprints. |
| Prompt | azmod reads the list at most once a second and waits until no deck has a track loaded (a deck state it cannot read counts as loaded). It then shows a yes/no dialog titled "Remote access": "Allow remote access (SSH) for key SHA256:...? Only allow a key you added yourself.", with the fingerprint cut to 32 characters, Cancel focused and BACK as Cancel (`src/azmod/ssh_approve.c`, `ssh_approve_logic.h`). Each fingerprint is asked about at most once per EP147 start, up to 8 keys; while another dialog is open, the question waits. |
| Allow | writes the fingerprint to `/run/az-ssh/approve`. The path unit runs the hook as `approve`: it appends the key's `<type> <base64>` line to `/home/root/settings/az-ssh-approved` (`.new`, then rename), removes it from `pending`, installs it and restarts `az-dropbear.service`. A fingerprint that is not pending changes nothing. |
| Cancel | writes nothing: the key stays pending and is asked about again at the next EP147 start |

| Allowed list | |
|---|---|
| File | `/home/root/settings/az-ssh-approved`, one `<type> <base64>` line per key; survives reboots and updates |
| First run | if the file does not exist and the deck already has `/home/root/settings/az-dropbear` (SSH was on before), the USB's current keys are allowed as they are; otherwise the list starts empty |
| Still needs the USB | an allowed key logs in only while the picked USB carries it and `ssh.enable` |
| Removed by | `MODS/uninstall` ([Uninstall](#uninstall)); removing `ssh.enable` turns SSH off and keeps the list |

Compare the fingerprint with `ssh-keygen -l -f <key>.pub` before allowing it.

dropbear listens on every interface, Wi-Fi included: Wi-Fi is how a computer reaches the
deck, its address comes from DHCP after the hook runs, and dropbear binds addresses, not
interfaces.

## How the deck boots with the USB

### What the firmware installs

| Path (`deck/payload/`) | Role |
|---|---|
| `usr/sbin/az-usbload` | the bootstrap loader |
| `usr/sbin/az-usbpick` | the USB pick, sourced by the loader |
| `home/root/scripts/usb-renotify.sh` | re-announces mounted sticks to EP147 |
| `etc/systemd/system/az-usbload.service` | runs the loader once per boot, `Type=simple`, ordered `After=EP147.service` with no dependency, so a crashing mod set cannot stop the loader from running and recovering the deck |
| `etc/systemd/system/EP147.service.d/10-azmod.conf` | reads `/home/root/settings/az-usbload/az-preload.env` as an environment file, and runs `az-usbload --post-start` in the background after every EP147 start |

EP147 is the deck software. `az-bootlog` and its unit are in the tree but left out of the
release build.

**EP147 never waits for the USB.** Every boot starts EP147 with the set the loader applied
last time, read from the settings partition, with no USB access before it starts. The loader
then runs alongside it, works out which set the USB asks for, and acts only if that
differs. The same USB as last time costs no write and no restart.

### Step by step

1. **Pick one USB** (`az-usbpick`). Only USBs the deck software has already mounted
   count (their `/proc/mounts` entry); the loader never mounts a USB itself. A partition is
   a candidate when its `MODS/` holds a core (`azmod.so` or `azmod-core.so`) or one of the
   files that act without one: `azmods.cfg`, `uninstall`, `logo.restore`. An
   empty `MODS/`, or one holding only `community-mods/`, `deck/` or other files, is not: the app
   creates `MODS/` on every USB it prepares, and nothing loads community mods or runs the
   deck scripts without a core. Labels play no part; the physical port decides:

   | Rule | Detail |
   |---|---|
   | USB1 wins | USB2 is used only when USB1 has no USB, when every partition on the USB in USB1 is mounted and none is a candidate, or when the wait runs out |
   | Ports | identified as the deck software identifies them for `/proc/udev_usb1` and `/proc/udev_usb2`: USB bus paths `1-1` and `3-1` are USB1, `2-1` and `4-1` are USB2 |
   | Other paths | a USB behind a hub has an unknown port and is ignored |
   | Wait | up to 10 seconds for any USB, up to 25 seconds for a USB in USB1 that is still mounting |
   | Several partitions | the first mounted candidate is used |

   The loader, the hooks (`AZ_MNT`), the on-deck updater and the community mods fetcher all
   use this one pick; the watcher picks again before each request. A switch counts on its
   own: a USB in USB1 carrying only a `MODS/azmods.cfg` with `mods = off` wins over a mods USB
   in USB2 and boots the deck stock, so mods can be turned off from any USB.

2. **Copy `MODS/deck` to RAM, check it against its pins**, and update the cache
   ([`deck/`](#deck-the-deck-side-scripts)). With no USB, the cached copy is checked and
   used.

3. **Read the switches** in `azmods.cfg` (`mods`, `deck`, `community-mods`). **Hand over to the
   USB's loader** when `deck/az-usbload` is pinned, parses, and neither `mods = off` nor
   `deck = off` is set. The rest of the boot is the USB's copy, which then syncs
   `azmods.cfg` ([`azmods.cfg`](#azmodscfg-settings-and-switches)).

4. **Decide the set.** Stock (preload nothing) when:
   - there is no candidate USB;
   - `azmods.cfg` says `mods = off`;
   - `uninstall` is present;
   - `MODS/` holds no usable `.so`;
   - no `.so` is pinned by genuine trust pins (an unpinned `.so` is skipped as if absent);
   - no core (`azmod-core.so` or `azmod.so`) is left.

   Otherwise the set is the core plus `azstem.so` when present.

5. **Stage the files** into the cache, `/home/root/settings/az-usbload/` on the settings
   partition (p7):
   - each pinned `MODS/*.so` is compared with the cached copy by md5 and copied only when it
     differs (written as `<name>.new`, checked against its pin again, then renamed). A cached
     `.so` no longer on the USB is deleted. A failed copy keeps what EP147 already loaded
     and ends the loader for this boot;
   - `azmod-pngpatch/` and `community-mods/` are compared as whole trees (an md5 over every
     file's md5) and replaced only when they differ;
   - the cache's `community/enabled` and `<id>/<id>.off` (what the core reads) are written
     from the `community-mods.<id>` keys;
   - `community-mods = off` removes the cache's `community/` and writes
     `az-usbload/community-mods.off`, so the Mod Menu says "disabled" rather than "none
     installed".

6. **Write `.deck-info`** when its content would change.

7. **Crash-loop check.** If `MODS/.mods-disabled-crashloop` matches this set, the set
   becomes stock for this boot ([The crash-loop guard](#the-crash-loop-guard)).

8. **Compare with what is running.** The preload line is
   `LD_PRELOAD=/home/root/settings/az-usbload/azmod.so:/home/root/settings/az-usbload/azstem.so`
   (empty for stock). If it equals the line in `az-preload.env` and no cached file changed,
   the loader runs the hooks, clears `.pending-powercycle` and stops there: no write, no
   restart. Otherwise it writes the new line to `az-preload.env` (by rename) and continues.
   An uninstall boot does not write it (the hook deletes the cache).

9. **Run the hooks** in `deck/boot.d`.

10. **Restart EP147, if the [restart policy](#the-restart-policy) allows it.** First, if
    EP147 has already failed (its start limit reached), the loader acts at once: the
    crash-loop guard trips when the set has mods, otherwise EP147 is restarted. Then the
    restart waits until systemd has finished booting (`running` or `degraded`), EP147's
    `HuiProcessor` thread exists, and either Wi-Fi has associated or EP147 has been up 30
    seconds (`AZ_EP147_SETTLE`): a restart before EP147 has loaded its settings can lose the
    stored Wi-Fi password, and one during the boot transaction can hang the boot. If these
    do not all hold within 120 seconds (`AZ_GATE_MAX`), there is no restart; the new set
    applies at the next EP147 start, since the environment file is already written.

    Before restarting, the loader creates `/run/az-reloading` (a running azmod shows its
    RELOADING... banner) and waits 1.5 seconds; a track loaded in that time cancels the
    restart. For a set with mods it writes a runtime drop-in that disables core dumps for
    EP147 ([The crash-loop guard](#the-crash-loop-guard)). It removes the community start
    quarantine's `.starting` marker (a deliberate restart is not a crash), then runs
    `systemctl daemon-reload` and `systemctl restart EP147.service`.

11. **Confirm it came back.** Success is a new EP147 process with its `HuiProcessor` thread
    within 45 seconds (`AZ_ACTIVE_WAIT`). On success the loader re-announces the mounted
    sticks to EP147 6 and 16 seconds later (EP147 forgets mounted media on a restart) and
    then the computer link, and clears `.pending-powercycle` and `.mods-disabled-crashloop`.
    On failure it writes `.pending-powercycle`.

12. **Keep watching.** The loader stays running while `deck/lib/az-modupdate`,
    `deck/lib/az-community` or `deck/lib/az-savelogs` is present, or while a held-back restart
    waits:

    | Job | Detail |
    |---|---|
    | Updates screen | serves `/run/az-modupdate.req` with `lib/az-modupdate`; after an install, re-runs the loader from the top to stage the new set |
    | Community Mods screens | serves `/run/az-community.req` with `lib/az-community`, one request at a time; an `apply` re-runs the loader and restarts EP147 |
    | System Info screen | serves `/run/az-savelogs.req` with `lib/az-savelogs`, passing it the loader's own answer to whether every deck is empty ([Save Logs to USB](LOGS.md#save-logs-to-usb)) |
    | Update check | about 45 seconds after each EP147 start, then every 30 minutes, while Wi-Fi is up and a mods USB is in |
    | Held-back restart | applies it once every deck is proven empty (checked every 5 seconds) |
    | `.deck-info` | rewrites the `fwtag=` line once the core reports it |

### The restart policy

The mods are preloaded, so a changed set needs an EP147 restart, and a restart drops every
loaded track. The loader restarts EP147 on its own only in these cases:

| Situation | Restart |
|---|---|
| EP147 is already running mods (the env it started with is not empty) | never by the loader. The new set is staged and waits for the user's Reload or the next boot. |
| EP147 is running stock (a fresh install, or the boot after mods were off) | once, on the boot's first pass while the deck has been up at most 240 seconds (`AZ_BOOT_WINDOW`), unless a track is known to be loaded; later only on proof that every deck is empty, held for 3 seconds (`AZ_DECKS_SETTLE`) |
| The USB asks for `mods = off` or `uninstall` | allowed, under the same early-boot or every-deck-empty rule (these are the user's requests, and `mods = off` is the way out of a bad set) |
| A set installed from Mod Menu > Updates | never: staged, and the Updates screen says "Update installed. Reload to apply." |
| Community Mods' apply | the user's own Reload: the Mod Menu asks for confirmation when a track is loaded (or that cannot be told), and the loader restarts without checking the decks |
| No USB, no `MODS/`, no usable core | not a request: the running set carries on; the stock env applies at the Reload or the next boot |

While a restart waits, `/run/az-reload-pending` exists (first line `stick`, or `update` for
a staged update) and the Mod Menu's Reload row says "Reload to apply.". Any EP147 start
loads the waiting set and removes the file.

**Proof that a deck is empty** comes from azstem, which reads each deck's loaded-track
record inside EP147 (an all-zero track ID is an empty deck) about once a second and rewrites
`/tmp/az-decks` (temporary file plus rename) on every change and at least every 3 seconds:

```
azdecks 1
pid 1234
up 812.43
decks EELE
```

| Field | Meaning |
|---|---|
| `pid` | the EP147 process the file describes; any other pid makes the file unknown |
| `up` | `/proc/uptime` when written; more than 10 seconds old (`AZ_DECKS_FRESH`) makes the file unknown |
| `decks` | one letter per deck: `E` empty (on two samples in a row, since a track change passes through an empty record), `L` loaded, `U` unknown |

No file (stock EP147), another pid, a stale file or any `U` counts as unknown, and unknown
never counts as empty. EP147 keeps no file open on the USB for a loaded track, so its open
files cannot prove a deck empty; an audio file it does hold open under `/media` still counts
as loaded.

### The crash-loop guard

A set that crashes EP147 at start would crash it from the first start of every boot,
because EP147 reads `az-preload.env` before the loader runs. systemd restarts EP147 on
failure and marks the service failed once its start limit is reached. The guard in
`deck/payload/usr/sbin/az-usbload` trips before that, and does not depend on firmware
identification.

| | Detail |
|---|---|
| Trips when | EP147 restarted at least `CLGUARD_N` times (default 3, `AZ_CLGUARD_N`), counted by `systemctl show EP147.service -p NRestarts`, while the running EP147 has no thread named `HuiProcessor` (it never finished starting) |
| Watched | during the loader's wait for its own restart (`AZ_ACTIVE_WAIT`, 45 seconds); and, on a boot with a non-stock set, for `CLGUARD_T` seconds (default 40, `AZ_CLGUARD_T`) once the watcher starts, ending early when EP147 is up with no new restarts. The second watch runs only while the loader stays up to watch (step 12). |
| Also trips when | EP147 is already in the failed state and the set has mods |
| Action | empties `az-preload.env` (the next start is stock), writes `MODS/.mods-disabled-crashloop` holding the set's signature (the md5 of the sorted `md5sum` lines of the USB's `MODS/*.so`), runs `systemctl reset-failed` and restarts EP147 |
| Afterwards | a USB whose set has that signature is staged as stock without being tried. Changing any `.so` changes the signature; deleting the file does the same. A set with mods that comes back healthy after the loader's restart clears the file. |
| Core dumps | before restarting into a set with mods, the loader writes `/run/systemd/system/EP147.service.d/50-az-nocore.conf` (`LimitCORE=0`): a crash-looping EP147 otherwise writes one core per crash into the RAM root file system and can exhaust memory before the guard acts |
| Test | `sh deck/test/clguard.sh` ([TESTING.md](TESTING.md)) |

Community mods have a finer guard inside the core: the start quarantine and crash blame in
[COMMUNITY-MODS-INTERNALS.md](COMMUNITY-MODS-INTERNALS.md#quarantine-and-crash-blame).

### What a plain EP147 restart does not redo

The Mod Menu's Reload row, an automatic restart after a crash, and a manual
`systemctl restart EP147.service` all start EP147 with whatever `az-preload.env` names.
None of them:

- picks a USB again, compares md5s or copies anything into the cache;
- reads `azmods.cfg`, `uninstall` or any other switch;
- runs the boot hooks;
- mirrors `community-mods/`.

Only `az-usbload --post-start` runs: it removes `/run/az-reload-pending` and re-announces
the mounted USBs and the computer link to the new EP147. It does nothing on the first
start of a boot or during the loader's own restart. To make the deck pick up a changed
USB, power-cycle it. The Updates and Community Mods screens are the exception: their
install and apply steps re-run the loader from the top. An update is then staged and Reload
loads it; a community apply restarts EP147 at once.

### Logs

The loader, the hooks and the helpers log to `/tmp` (RAM), each capped by
`deck/lib/az-logcap.sh`; the loader also keeps a copy of the last boots on p7 that survives a
power-off. Every log on the deck, with its size limit and how long it is kept, and how to collect
them for a bug report: [LOGS.md](LOGS.md#deck-scripts). The loader sources the cap helper only
from a copy the signed pins cover; a firmware copy of a script that runs before any set was
staged has no helper and no cap.

The mods write no diagnostic logs unless `/home/root/settings/azmod-logs.on` exists when
EP147 starts ([Flag files](#flag-files)).

## Turning mods off and on

| To | Do | What happens |
|---|---|---|
| turn mods off | set `mods = off` in `MODS/azmods.cfg` (the app's switch does this), power-cycle | the boot starts with the old set, then the loader restarts EP147 stock once (restart policy). The cache stays on the deck. |
| turn them back on | set `mods = on` (or delete the line), power-cycle | the boot starts stock; the loader writes the set back and restarts EP147 once |
| run without the deck scripts | set `deck = off` | the mods load; the USB's loader and hooks do not run |
| turn community mods off | set `community-mods = off` | the official mods load, no community mod does |
| go back to stock for good | [Uninstall](#uninstall) | |

**Removing the USB.** Pulling the USB while the deck runs changes nothing about the
mods: they run from the cache. What lives on the USB goes with it: stems and drum roll
samples on that USB, and community mods' `assets_dir` and `data_dir` (they read as
unavailable). At the next boot EP147 starts with the cached set, the loader finds no mods
USB, writes an empty `az-preload.env` and does not restart (a missing USB is not a
request); the Reload row says "Reload to apply.", and the boot after that starts stock. The
cache and the cached `deck/` stay on the deck, and the cached hooks still run (the SSH hook
turns SSH off when there is no USB).

**Recovering a deck whose mods misbehave.** On a computer, add the line `mods = off` to
`MODS/azmods.cfg` (or create the file with just that line), or remove the USB, and
power-cycle. The loader runs even when EP147 is crash-looping and writes an empty
`az-preload.env`, so EP147's next start is stock. When the loader could not restart EP147
itself (`.pending-powercycle`), it can take a second power-cycle to come up without mods.

## Uninstall

`MODS/uninstall` asks the deck to remove every trace of AZ-MODS so that stock firmware can
be flashed. On the next boot with that USB:

1. the loader stages nothing, leaves the deck cache alone and does not write the
   environment file;
2. `20-bootlogo.sh` restores the stock boot logo when an early AZ-MODS firmware had
   replaced it;
3. `30-uninstall.sh` deletes the AZ-MODS files from the settings partition: an explicit list
   plus everything matching `azmod*`, `azstem*`, `az-usbload*`, `az-restart*` and
   `az-bootlog.log`, including files left by development builds. Every name must start with
   `az`, so the deck's own files (`SETTINGS.DAT`, `wifi.json`, `bluetooth_snk.json`,
   `cabinet.img`, `cabinet/`) can never match. The boot logo backup is kept unless that
   boot's log shows the logo is stock again;
4. the loader restarts EP147 stock (restart policy), then runs `30-uninstall.sh` once more
   to remove the files the mods recreated while they were still running.

The result is `MODS/.uninstall-result`: five `key=value` lines, always all present and in
this order, LF line endings, ASCII.

```
result=CLEAN
removed=az-usbload azmod.cfg azstem.enable ...
remaining=
failed=
message=No AZ-MODS files remain on the deck. You can now flash the stock firmware.
```

| Key | Meaning |
|---|---|
| `result` | `CLEAN` (safe to flash stock) or `INCOMPLETE` |
| `removed` | names removed by this run, space separated; empty when there was nothing to remove |
| `remaining` | AZ-MODS names still on the settings partition |
| `failed` | names that could not be removed |
| `message` | one sentence for the user; always last, may contain spaces |

## Settings kept on the deck

The mods keep their settings on the deck's settings partition, `/home/root/settings` (p7).
`azmod.conf` is the deck's working copy of the USB's
[`azmods.cfg`](#azmodscfg-settings-and-switches), which wins; everything else here stays
with the deck.

p7 is about 61 MB and also holds the deck's own `SETTINGS.DAT`, `cabinet.img` and analysis
cache; a full p7 breaks the deck's BPM display. The loader keeps its cross-boot log under
32 KB and the community mirror keeps 12 MB free for that reason.

### `azmod.conf`

The Mod Menu's state (`src/azmod/azconf.h`, `azconf.c`). Written by azmod whenever a setting
changes; read once at start, and again when the loader hands over a changed `azmods.cfg`
(`/run/azmods-cfg.import`; one azmod cannot load is renamed `.bad` and both copies stay as
they are). A save writes `azmod.conf.new`, fsyncs it, renames it over
`azmod.conf` and fsyncs the directory, so a power cut leaves either the previous settings or
the new ones. Edit it only with EP147 stopped.

```
# AZ-MODS settings
version = 1
stems = on
drum-roll-bank = 0
padcolor.on = on
padcolor.0 = native
pinned = stems
```

| Rule | Detail |
|---|---|
| Lines | `key = value`; whitespace around `=` and at both ends of a line is ignored. `#` starts a comment only at the start of a line; a `#` after a value is part of the value. Comments and blank lines are kept on rewrite. |
| Keys | `[a-z0-9._:-]+`; `:` is reserved for community mods' keys, `<mod-id>:<key>` |
| Version | a file without a valid `version = 1` line is invalid and treated as absent (rebuilt from `azmod.cfg`). A higher version (from a newer version of the mods) is read through `azmod.cfg` and never overwritten. |
| Duplicates | the last one wins; a rewrite keeps only the winner |
| Unknown keys | kept as they are (a newer version's settings survive a rollback) |
| Bad lines | a line over 511 bytes, with control bytes, not UTF-8, or neither a comment nor `key = value` is ignored and dropped on the next save |
| Size | a file over 64 KB is invalid |
| Bad values | a value that does not parse takes that setting's default |

| Key | Value |
|---|---|
| one per Mod Menu setting | listed in [MOD-MENU-KEYS.md](MOD-MENU-KEYS.md). A toggle is `on` or `off`; a choice is its number. |
| `padcolor.on` | the Pad Colors switch |
| `padcolor.0` to `padcolor.3`, `padcolor2.0` to `padcolor2.3` | each pad mode's color, `native` or an index into the [palette](#line-2-pad-colors), in the order HOT CUE, BEAT LOOP, SLIP LOOP, BEAT JUMP; `padcolor2.*` are their second pages |
| `pinned` | the pinned rows, by key, comma separated (shown as SOURCE rows while `azmod-pinrows.on` exists) |
| `theme` | the theme: `day`, `azmods`, `midnight`, `ember` or `forest`. Absent or unknown: `day`. Picking a theme also turns Themes on. |
| `vinyl.brake` | Fine Vinyl Speed Adjust's slider value, `0.00` to `1.00`. Empty, missing or out of range: the deck's stock values. |
| `wave.zoom` | the waveform zoom Remember Waveform Zoom last saved: `2/1`, `1/1`, `1/2`, `1/4`, `1/8` or `1/16`. Written only while that row is on; missing or anything else: nothing is restored. |
| `bluetooth.channel` | a copy of `azmod-btchannel`, which stays the file azmod reads. Refreshed at every start and every save; empty means the file is absent (the default). |
| `legacy.cfg-hash` | an FNV-1a hash of the `azmod.cfg` azmod last wrote. When `azmod.cfg` no longer matches, another version wrote it (going back to 1.2.2, then updating again): azmod takes every setting `azmod.cfg` holds from it, keeps the rest of `azmod.conf` (settings 1.2.2 does not have, community mods' rows, their pins) and saves. |
| `<mod-id>:<key>` | a community mod's own rows; kept when the mod is removed, so reinstalling it restores them |

**First start after an update from 1.2.2 or older:** there is no `azmod.conf`, so azmod reads
`azmod.cfg` and its small files (`azmod-theme`, `azmod-vinyl.v`, `azmod-btchannel`, and the
old `azmod-plreorder.on` / `azmod-rowcache.on` / `azmod-touchaccum.on` flags), writes
`azmod.conf` from them, and leaves the old files as they are. An `azmod.conf` without a
`theme` or `vinyl.brake` key (written before those moved into it) takes that key once from
`azmod-theme` or `azmod-vinyl.v`; azmod does not read or write those two files after that.

### `azmod.cfg`

The Mod Menu's state as 1.2.2 and older keep it. azmod still writes it in exactly that
format at every save (so going back to 1.2.2 keeps the current settings), and reads it only
to build `azmod.conf`. Each save writes `azmod.cfg.new`, flushes it and renames it over
`azmod.cfg`. Up to three lines:

```
100000110001000000000000100001000000000
-1 -1 4 -1 1 -1 -1 -1 -1
0
```

setting its default. A shorter valid line (from an older version) is read as far as it goes
and the newer settings take their defaults. A longer line (from a newer version) is read for
the settings this version knows.

#### Line 2: pad colors

Nine integers separated by spaces:

```
<HOT CUE> <BEAT LOOP> <SLIP LOOP> <BEAT JUMP> <enabled> <HOT CUE 2> <BEAT LOOP 2> <SLIP LOOP 2> <BEAT JUMP 2>
```

Each color is `-1` (the deck's own color) or a palette index. `<enabled>` is the Pad Colors
master switch, `1` or `0`. Missing fields take their defaults (`-1`, enabled `1`); an
out-of-range index reads as `-1`. Default: `-1 -1 -1 -1 1 -1 -1 -1 -1`.

| Index | Color | Index | Color | Index | Color | Index | Color |
|---|---|---|---|---|---|---|---|
| 0 | red | 7 | cyan | 14 | white | 21 | purple |
| 1 | orange | 8 | sky | 15 | gold | 22 | orchid |
| 2 | amber | 9 | blue | 16 | chartreuse | 23 | fuchsia |
| 3 | yellow | 10 | indigo | 17 | spring | 24 | rose |
| 4 | lime | 11 | violet | 18 | teal | 25 | peach |
| 5 | green | 12 | magenta | 19 | azure | 26 | pale mint |
| 6 | mint | 13 | pink | 20 | royal | 27 | lavender |

The RGB values are `AZMOD_PAD_PALETTE` in `src/azmod/pad_palette.h`. Indices are stable; new
colors are appended.

#### Line 3: pinned items

A decimal bit mask, bit *i* for mod *i*. Pinned items show as rows in the SOURCE list only
while `azmod-pinrows.on` exists. Default `0`.

Lines 2 and 3 are read only when line 1 is valid.

### Files written by the mods

These hold state. Each is written by the mods themselves; editing one by hand is either
undone or harmless. `azmod.conf`, `azmod.cfg`, `azmod-btchannel`, `azstem.enable`,
`azstem.stems*`, `azstem.avail*` and `azstem.curtrack*` are replaced whole (written as
`<name>.new`, then renamed), so a reader never sees a half-written file; the first three are
also flushed before the rename. A leftover
`<name>.new` after a power cut is overwritten by the next save.

| File | Written by | Content and effect |
|---|---|---|
| `azmod.conf`, `azmod.cfg` | azmod | [above](#azmodconf) |
| `azmod-btchannel` | azmod | `3` or `4`: the mixer channel last set to Bluetooth (Remember Selected Channel). Absent: none. |
| `azmod-preview` | azmod | `1` or `0`: the Browse PREVIEW button's state when it was last pressed, set again at the next start. Absent: the deck's default (on). |
| `azmod-subcolumn` | azmod | the sub column the Browse header's sort menu button last chose, as its number in that menu (`0` = Default, no sub column), chosen again on the first track list after a start |
| `azmod-colwidths` | azmod | Column Edit: the widths given to Browse track list columns, as `<column id>:<width>` pairs. A damaged file sets no width. Applied only while Column Edit is on. |
| `azmod-colfields` | azmod | Column Edit: the field each Browse track list column shows instead of its own data, one `<column id> <field>` line per column. A damaged file sets no field. Applied only while Column Edit is on. |
| `azmod-colshow` | azmod | Column Edit: the columns hidden or shown with it, a sum of 1 artwork, 2 track number, 4 BPM, 8 Key, plus 16 times the same sum for the columns set (the others stay as the deck shows them in each list). Applied only while Column Edit is on. |
| `azmod-community/` | azmod, `az-community` | community mods' state: `approved` (one `<id> <sha256 of <id>.so>` line per mod, at most 64, written under the lock `.approved.lock`; `.approved-init` marks that mods installed before the list existed were approved once), `<id>.cfg` (each mod's settings, `key=value` and `key$=text` lines), `<id>.owner` (the repository whose mod owns those settings; another repository's set-aside settings are `.<id>@<hash>.cfg`), `off` (the Mod Menu's community switch), `.trusted` (the one-time warning was confirmed), and the crash guard's `.starting`, `.crashes`, `.blame`, `.initing` and `<id>.crashed` ([COMMUNITY-MODS-INTERNALS.md](COMMUNITY-MODS-INTERNALS.md#quarantine-and-crash-blame)) |
| `azstem.enable` | azmod | `1` or `0`: the Stems master switch, read by azstem |
| `azstem.stems`, `azstem.stems2`, `azstem.stems3`, `azstem.stems4` | azmod | decks 1 to 4: a decimal mask, bit 7 = stems engaged (the Stems switch is on and that deck's track has stems), bits 0 to 3 = vocals, other, bass, drums on |
| `azstem.avail` ... `azstem.avail4` | azstem | `1` when the deck's loaded track has stems, else `0` |
| `azstem.curtrack` ... `azstem.curtrack4` | azstem | the deck's loaded track key (empty when none). azmod turns that deck's stems back on when it changes. |
| `az-usbload/` | loader | the cache: the staged `.so` files, `azmod-pngpatch/`, `community/`, `community-mods.off`, `deck/`, `az-preload.env`, `usbload.log`, and `cfg.sync` (the md5s of the USB's `azmods.cfg` and the working copy at the last sync) |
| `az-dropbear/` | `10-sshgate.sh` | this deck's dropbear host keys |
| `az-ssh-approved` | `10-sshgate.sh` | the SSH keys allowed on this deck ([Allowing a key](#allowing-a-key)) |
| `az-bootlogo/`, `az-bootlogo.log` | early AZ-MODS firmware, `20-bootlogo.sh` | the stock boot logo backup (`orig/`), the bytes a restore replaced with its journal (`undo/`), and the hook's log |
| `az-uninstall.log` | `30-uninstall.sh` | kept only when an uninstall was INCOMPLETE |

`az-preload.env` holds one line, `LD_PRELOAD=...` or empty; empty or absent means stock.
The `azstem.*` files are how the two mods talk to each other; each side polls the other's.

### Flag files

Read by release builds and created by hand (over SSH) or not at all. All are absent by
default, so absent always means the shipped behavior. Options and kill switches are tested
for existence only. Most are read once when EP147 starts, so restart EP147 after changing
them; `azmod-daymode.on`, `azmod-ovstrip.off` and `azmod-pinrows.on`, among others, are
polled while EP147 runs.

**User options**

| File | Effect |
|---|---|
| `azmod-logs.on` | turns on the mods' diagnostic logs (under `/tmp`, each size-capped). azmod and azstem read it at start; the community core checks it once a second ([LOGS.md](LOGS.md#with-diagnostics-on)). |
| `azmod-pinrows.on` | shows pinned Mod Menu items (`pinned` in `azmod.conf`) as rows in the SOURCE list |
| `azmod-themes.off` | installs none of the Themes hooks. The Themes row still shows but does nothing. |

**Developer override**

| File | Effect |
|---|---|
| `azmods-unsigned.on` | the loader runs and stages everything without the trust check, and logs `trust: DEVELOPER OVERRIDE` every boot. Read by the loader at every boot; the same name on a USB does nothing. [UPDATES-AND-SIGNING.md](UPDATES-AND-SIGNING.md) |

**Kill switches.** Each turns off one piece of a feature that is otherwise always on, without
a rebuild; with one present, the deck behaves as stock for that piece.

| File | Turns off |
|---|---|
| `azmod-srcrow.off` | the MOD MENU row in the SOURCE list (the way into the Mod Menu) |
| `azmod-stemnative.off` | the native stem pad grid (the deck's own pad widget showing stems) |
| `azmod-stemforge.off` | the forced refresh that fills the native stem pad tiles |
| `azmod-stems4.off` | the stem strip in the 4 DECK layout's per-deck info cell |
| `azmod-preview.off` | remembering the Browse PREVIEW button's state (`azmod-preview`) |
| `azmod-subcolumn.off` | remembering the Browse sub column (`azmod-subcolumn`) |
| `azmod-coledit.off` | Column Edit: no COLUMN EDIT button, and no saved widths, fields or hidden columns applied |
| `azmod-colfields.off` | Column Edit's fields (each column keeps its own data) |
| `azmod-stemsmark.off` | the stem marks in track and playlist rows, whatever the Stem Marks switch says |
| `azmod-wavemute.off` | waveform scaling by which stems are on |
| `azmod-wscale.off` | the per-render waveform scaling path (falls back to per-point hooks) |
| `azmod-wpfast.off` | azmod's faster re-implementation of the waveform point accessors (uses the deck's own) |
| `azmod-dedupe4.off` | skipping the deck software's duplicate rebuild of deck 4's waveform |
| `azmod-gridaa.off` | Bright Grid: the beat grid brightening while a deck moves |
| `azmod-scroll60.off` | the 60 FPS list scrolling part of 60 FPS UI |
| `azmod-ovstrip.off` | Themes' handling of the deck overview strips |
| `azmod-menub3.off` | the extra COPY / PASTE button in the browse MENU popup |
| `azmod-folderpreview.off` | filling the preview pane for a selected folder (firmware 2.00 only) |
| `azmod-drumsel.off` | recoloring the drum roll pad tiles to show the selected sample |
| `azmod-btreset.off` | resetting the Bluetooth controller's UART speed before EP147 opens it |

**Tuning values.** Read with a value inside; out-of-range values are ignored.

| File | Content |
|---|---|
| `azmod-ui60.ms` | the 60 FPS repaint period in ms, 14 to 20 (default 16) |
| `azmod-brightgrid.cfg` | Bright Grid: `<gain 1.0-2.0> <overdrive 1.0-2.5> <gray 0-96> <move ms 17-1000> <ramp ms 1-2000>` (defaults 1.1, 1.3, 0, 40, 60). Checked once a second: a new, changed or removed file applies within about a second. Without the file the defaults apply. |
| `azmod-xpad` | the X-PAD's bytes on the mixer bus: `<position> [touch] [touch mask] [full scale] [zone]` (defaults 0x1d, none, 0xff, 128, 0x1e), for a deck where the defaults are wrong |
| `azstem.drumsyncoffset` | Beat Sync correction in samples at the track's own sample rate, may be negative (default 0). Read while EP147 runs. |

**Diagnostic and test inputs.** Release builds read these for diagnosing a deck in the
field. They are not settings: leave them absent.

| File | Effect |
|---|---|
| `azstem.track`, `azstem.stemsdir` | `azstem.track`: a track key for deck 1 when its loaded track yields no name; `azstem.stemsdir`: a stems folder to use when no stems base is found. `/tmp/azstem.track` and `/tmp/azstem.stemsdir` are read when these are absent |
| `azmod-daymode.on` | Themes on regardless of the Mod Menu |
| `azmod-onelibrarykey.on` | emulator only: it substitutes the OneLibrary database key in EP147's own database connections. Never create it on a deck. |

azstem's other diagnostic and test inputs (address overrides, observers, probes, the test
tone, the drum test, the mute mask, manual key and BPM overrides) and azmod's
`AZ_PROBE_ON()` probes exist only in development builds (`AZMOD_RELEASE=0`, or
`AZMOD_PROBES=1`); a release build never reads them.

Older flags are migrated once, into `azmod.conf`: an `azmod.cfg` line 1 too short to hold the
Playlist Editing switch takes that switch's state from `azmod-plreorder.on` (which azmod no
longer writes), and one too short to hold 60 FPS UI turns it on when `azmod-rowcache.on` or
`azmod-touchaccum.on` exists. A line 1 too short to hold the Overlays switch turns Overlays on
when FPS is on, and one too short to hold Remote Stems turns Remote Stems on (its default).

Art is read from the first of `/home/root/settings/az-usbload/azmod-pngpatch` (the loader's
cache), `/home/root/settings/azmod-pngpatch` and `/tmp/azmod-pngpatch` that exists.

## What survives a reboot

| Location | Reboot | Firmware update | Holds |
|---|---|---|---|
| the USB | yes | yes | everything under `MODS/`, `STEMS/`, `DRUM ROLLS/` |
| `/home/root/settings` (p7) | yes | yes | `azmod.conf`, `azmod.cfg` and the other settings, the loader's cache, `az-preload.env`, SSH host keys, community mod state. Only `MODS/uninstall` removes them. |
| `/tmp`, `/run` (RAM) | no | no | the RAM copy of `MODS/deck`, every log under `/tmp`, the Updates, Community Mods and Save Logs status files, `/run/az-reloading`, `/run/az-reload-pending`, `/tmp/az-decks`, the SSH units and the copied dropbear binary |
| the rest of the root file system (RAM) | no | no | the installed SSH key, the hooks' runtime files under `/etc`; the hooks write them again every boot |

A power-cycle always re-runs the whole loader against the USB that is in the deck; Mod Menu
settings stay with the deck.

## Preparing a USB by hand

The minimum for mods to load:

1. A FAT32 or exFAT USB the deck mounts, in USB1 (or USB2 with no mods USB in USB1; an
   empty `MODS/` folder on the USB in USB1 is fine).
2. `MODS/azmod.so`, and `MODS/azstem.so` for stems and Drum Roll, built from this source
   ([BUILDING.md](../BUILDING.md)) or taken from a release.
3. `MODS/deck/` and `MODS/azmod-pngpatch/` (from the release) for the full feature set:

   ```sh
   python3 deck/stage_stick.py <stick>/MODS/deck --version <x.y.z>
   ```

   `stage_stick.py` takes `lib/az-handoff-guard` from `src/out/`, so build it first
   (`make -C /g CC=gcc azhandoff` in the build container, as in [BUILDING.md](../BUILDING.md)), or pass `--no-guard` to leave it out.
4. No `mods = off` in `MODS/azmods.cfg`, and no `uninstall` in `MODS/`.
5. Either an official set as released (its `deck/trust.pins` is signed), or, for your own
   builds, pins signed with your key for a loader built with it, or the developer override
   on the deck ([UPDATES-AND-SIGNING.md](UPDATES-AND-SIGNING.md)). A set without one of these
   boots the deck stock.

Power the deck on with the USB in. A deck running stock starts stock, then the loader
restarts EP147 once with the new set, early in boot and before a track is loaded. A deck
already running a set keeps it and stages the new one: the Reload row says "Reload to
apply.", and Reload or the next boot loads it. After that the same USB boots with no
restart.
